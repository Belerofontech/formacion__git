Testing

¿Por qué testing?

Charla libre. Ideas a tocar: depurar con pdb resuelve un error puntual, pero no evita que reaparezca; un test es la red de seguridad que permite tocar el código (refactorizar) sin miedo a romper algo sin enterarte; un error detectado ahora es barato, el mismo error en producción es caro; un test también documenta qué se espera de una función, de forma explícita y ejecutable (no un comentario que se queda desactualizado).

Ojo con los floats


            >>> 0.1 + 0.2 == 0.3
            False
Por cómo se representan internamente, dos operaciones con decimales que deberían dar el mismo resultado matemático pueden no ser iguales bit a bit. Especialmente relevante trabajando con importes, tipos de interés o cualquier cálculo financiero con decimales.

Testing, pero de los datos en vez del código

pandera declara el esquema que debe cumplir un DataFrame, igual que un type hint declara el tipo de un parámetro.

La sintaxis


            import pandera.polars as pa


            class Numeros(pa.DataFrameModel):
                valor: int = pa.Field(ge=0)
Mismo mecanismo que un type hint: nombre de columna, tipo, y opcionalmente un pa.Field con la restricción (ge, le, gt...). Esto es solo el mecanismo — el caso real va en la práctica.

Si da tiempo

No todo es comprobar un valor de retorno

A veces lo que importa es que la función falle de forma controlada ante una entrada inválida, no que devuelva cualquier cosa.

Práctica

practicas/testing/si_da_tiempo/operaciones.py


            def dividir(a: float, b: float) -> float:
                if b == 0:
                    raise ValueError("No se puede dividir por cero")
                return a / b

Testear dividir (ya escrita) — pista: pytest.raises


            pytest practicas/testing/si_da_tiempo
with pytest.raises(ValueError): falla el test si el bloque de dentro NO lanza ValueError. Solución en practicas/testing/si_da_tiempo/solucion/.
